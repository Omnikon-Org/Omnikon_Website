# Omnikon Content Standards & Strategy

## 1. Content Core Purpose
Omnikon's content exists to empower student developers, open-source contributors, and hackathon participants. Every article, guide, project breakdown, and track documentation must provide immediate, practical value to a software developer or learner.

---

## 2. Zero-Tolerance Rules

### STRICT PROHIBITIONS
- ❌ **No AI Fluff / Filler Text**: Never generate generic fluff like "In today's fast-paced digital world...". Jump straight to code, technical architecture, or actionable insights.
- ❌ **No "Lorem Ipsum" or Draft Placeholders**: Every live indexable page must contain complete, real content.
- ❌ **No Thin SEO Pages**: Do not create pages solely for keyword targeting or ad unit insertion without substantial technical material.
- ❌ **No Unverified Specs**: Project breakdowns must reflect real, existing repositories under `Omnikon-Org` (e.g., Astrodex, CNTRL, IssueSwipe).

---

## 3. Supported Content Types & Specifications

### A. Technical Blogs & Articles
- **Purpose**: Share technical tutorials, open-source guides, and engineering updates.
- **Mandatory Elements**:
  1. Author attribution & publication date.
  2. Platform source badge (`Dev.to`, `Hashnode`, `Medium`, `GitHub Pages`, `Personal Blog`).
  3. Code blocks with language syntax highlighting.
  4. Practical takeaway summary or conclusion.

### B. Hackathon Track & Event Documentation
- **Purpose**: Deliver clear hackathon mechanics, problem statements, and active timelines.
- **Mandatory Elements**:
  1. Timeline phases (Registration, Problem Statement Release, Submission, Evaluation, Winners).
  2. Real problem statement briefs with technical requirements and target impact.
  3. Clear links to submission repositories or judging portals.

### C. Open Source Project Breakdown
- **Purpose**: Showcase community projects (e.g. IssueSwipe, Astrodex, CNTRL) to attract contributors.
- **Mandatory Elements**:
  1. Project elevator pitch & target problem solved.
  2. Repository badge (GitHub link, tech stack, GSSoC/ECSoC participation status).
  3. "Get Started" contribution steps (e.g., beginner-friendly issues tag).
  4. Live demo links (where available).

### D. Developer Journey & Mentorship Tracks
- **Purpose**: Guide student developers from beginner to maintainer.
- **Defined Milestones**:
  - `Student` -> `Learner` -> `Builder` -> `Contributor` -> `Maintainer`.
- **Requirements**: Each milestone must list actionable skills, sample projects to build, and GitHub contribution expectations.

---

## 4. Tone of Voice & Editing Style
- **Developer-Centric**: Speak directly in software engineering terms (PRs, issues, APIs, deployments, architecture).
- **Encouraging & Student-Friendly**: Welcoming to beginners while maintaining technical accuracy.
- **Direct & Concise**: Clear headings, code snippets, bullet points, and high scannability.
